### 需求介绍
+ 居中对话框中 assistant 的 SSE 流式响应在实时渲染与历史恢复后，只要识别出可解析的文件路径、`file:///`、`http`、`https` 等目标，就不再以内文蓝色下划线文字路径作为最终展示形态，而是改为渲染为与用户输入框同风格的行内气泡
+ 本次改造范围仅针对 assistant 响应展示链路：
    + 实时 SSE 增量渲染中的 assistant 气泡
    + SSE 结束后持久化并再次恢复的 assistant 消息
    + 不要求改动用户输入框中已有气泡语义和用户消息正文的既有展示规则
+ URL/路径气泡只负责摘要展示，不得丢失完整值：
    + 文件类气泡展示文件名或末级路径摘要，超长时按现有气泡截断规则处理
    + `http/https` 类气泡展示可读摘要，允许裁剪显示
    + 每个气泡都必须保留原始完整 URL 或路径字符串，供复制、预览、打开、下载文件、打开目录等动作复用
+ 识别与归类继续复用现有消息 URL/路径提取规则，不额外放宽白名单：
    + 文件类继续支持现有绝对路径、`file:///`、`~/`、`/`、`skills`、`tmp`、`SOUL.md`、`USER.md` 等规则
    + `http/https` 类继续沿用现有资源类 URL 预览限制；资源类 URL 仍不可进入预览链路
+ 点击消息中的 URL/路径气泡时，需要直接弹出当前消息域已有的小气泡动作浮层，不再要求用户先双击或手动框选文本
+ 动作浮层顺序需要固定，`复制` 必须位于第一位，并且排在 `预览` 前面：
    + 文件/目录类：`复制`、`预览`、`下载文件`、`打开目录`
    + 普通 `http/https`：`复制`、`预览`、`打开`
    + 资源类 `http/https`：`复制`、`打开`
    + 目录类目标不展示 `下载文件`，也不展示无效 `预览`
+ `复制` 按钮行为：
    + 复制当前气泡绑定的完整原始 URL 或路径字符串到系统剪贴板，而不是复制气泡摘要文本
    + 成功后在左侧虚拟文件系统 Tips 位置提示 `已复制到粘贴板`
    + 失败时也需要给出明确 Tips 提示，不允许静默失败
+ 文件类气泡点击后出现的 `预览`、`下载文件`、`打开目录` 行为和出现条件必须与现有消息文件路径浮层保持一致，不得放宽或收紧
+ `http/https` 气泡点击后出现的 `预览`、`打开` 行为和出现条件必须与现有消息 URL 浮层保持一致：
    + `预览` 继续复用右侧 Sidebar 的独立 iframe 预览区
    + `打开` 继续复用现有新窗口打开逻辑
    + 现有可预览 URL 的自动右侧预览、失败回退、会话绑定和资源类 URL 过滤逻辑保持不变
+ 同一条 assistant 消息内存在多个可识别目标时，每个气泡都必须独立绑定自己的完整值和动作，不允许共用、串用相邻气泡的数据
+ SSE 增量分片过程中，URL 或路径可能跨 chunk 到达，最终展示结果必须以现有完整提取规则为准：
    + 不能因为分片中间态把半截路径错误渲染成气泡
    + SSE 结束前后的识别结果要稳定，不允许同一目标在文字链接和气泡之间来回闪烁
+ 与消息 URL/路径相关的既有新手引导、浮层层级和交互域隔离规则需要同步适配到新气泡方案，不得因从文字链接改成气泡而失效
+ 如仍存在未被本次气泡化覆盖的普通文字路径兜底场景，可继续保留现有双击/选中浮层逻辑，但不得影响新增气泡点击链路
+ restore 恢复链路需要同步补齐右侧 CLI 子任务 `cmd` 的历史重建能力：
    + 页面调用 `/api/restore` 拉取历史记录时，除了现有用户/assistant 消息恢复外，还要消费返回结果中的 `cli/get`、`cli/pub` 记录
    + `cli/get` 记录要视为一条待完成的 CLI 子任务 `cmd`，从原始 `content` 中尽量提取真实命令文本；需兼容直接 `{"cmd":"..."}`、嵌套 `message`、`messages[].content` 等现有日志形态
    + `cli/pub` 记录要作为上一条尚未完成的 CLI 子任务 `cmd` 的执行结果，优先提取可读文本；需兼容原始纯文本输出和 JSON 包裹的 `message/content/messages` 结构
    + 前端恢复后写入的数据结构、展示样式、复制到 `CMD` 输入框行为，必须与现有右侧 CLI 子面板中的 `cmd` 记录保持一致，不额外引入第二套渲染模型
    + 同一次 restore / 轮询续拉过程中，CLI 子任务 `cmd` 的恢复结果需要可去重、可增量：
        + 同一条 `cli/get` 记录不能因为重复 restore 被插入多次
        + 已恢复但尚未匹配到 `cli/pub` 的记录需要保持“执行中”态
        + 后续再次 restore 命中对应 `cli/pub` 后，需要就地补全为“成功/失败 + 输出结果”，而不是新增一条重复气泡
    + CLI 子任务 `cmd` 的恢复顺序必须与消息 restore 的时间线保持一致，仍按现有 `createdAt/id` 规则参与排序，避免右侧 CLI 子面板中的历史顺序跳动
    + 当 `cli/pub` 未找到可配对的待完成 `cmd` 记录时，前端可以忽略该条孤立结果，但不得影响本轮 assistant / user 消息恢复
    + 以上 restore 补齐逻辑只复用现有会话本地缓存、恢复轮询、CLI 子面板刷新和闪动提示链路，不新增独立接口或新的本地持久化通道

+ 以现有site页面技术栈编写以上代码，要求：
    + 在../../index.html中按现有HTML/CSS/JavaScript组织方式实现
    + 不引入新的构建流程和额外运行时依赖
    + 代码简洁，尽量复用现有SSE解析、assistant气泡渲染、思考片段展示、历史恢复、虚拟文件系统渲染和轮询状态同步逻辑
    + 能用现有开源包和浏览器能力的就不要重复造轮子
+ 最小范围更新
