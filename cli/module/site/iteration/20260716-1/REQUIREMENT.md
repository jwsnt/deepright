### 需求介绍
+ 页面心跳失败告警的阈值需要使用浏览器本地缓存，避免 integration 进程被强制关闭后无法读取 `/api/data` 中的配置而错误回退到其他阈值
    + 仅缓存 `config.json` 中的 `http.heartbeat` 数值及其缓存时间戳，不得缓存完整的 `config.json` 内容或其他配置字段
    + 缓存有效期固定为 `300` 秒；缓存未过期时直接使用缓存的阈值，不请求 `/api/data`
    + 缓存过期后才请求 `/api/data` 读取 `http.heartbeat`；读取成功且值为有效正整数时，更新数值和时间戳缓存后使用新值
    + `/api/data` 请求失败、响应解析失败、`http.heartbeat` 缺失或不是有效正整数时，心跳失败阈值必须回退为 `3`
    + `localStorage` 不可用、缓存内容解析失败、缓存时间戳无效或系统时钟异常时，必须安全回退为 `3`，不得抛出未处理异常或阻断心跳检测
    + 不需要按 API 地址、运行实例或页面会话区分缓存键
    + 配置变更的前端生效延迟最多为 `300` 秒
    + integration 已关闭时，若存在未过期缓存则继续使用该缓存；不存在有效缓存时按连续 `3` 次心跳失败触发告警
+ 心跳告警必须明确区分“转发服务心跳异常”与“integration 已关闭”，两类告警不得共用相同的文案或持续方式
    + `/api/heartbeat` 网络不可达、请求被拒绝或请求超时，才判定为 integration 已关闭；达到失败阈值后，告警标识文案从 `REMOTE SERVICE ALERT` 改为“本地应用已关闭”
    + integration 已关闭告警必须持续展示，不得沿用现有 `10` 秒自动隐藏逻辑；仅当 `/api/heartbeat` 恢复可通信时才允许关闭该持续告警
    + `/api/heartbeat` 可正常返回且响应中的 `status === 1` 时，判定为转发服务心跳异常，继续使用现有 `REMOTE SERVICE ALERT` 和短时心跳告警展示方式
    + `/api/heartbeat` 返回 HTTP 非成功状态时，说明 integration 仍在响应，不得判定为 integration 已关闭；继续按转发服务心跳异常处理
    + integration 恢复通信后，若转发服务仍有心跳异常，先关闭“本地应用已关闭”持续告警，再按转发服务异常的既有短时告警规则展示

### 编写代码
+ 以现有site页面技术栈编写以上代码，要求：
    + 在../../index.html中按现有HTML/CSS/JavaScript组织方式实现
    + 不引入新的构建流程和额外运行时依赖
    + 代码简洁，尽量复用现有知识库展开态、右侧边栏标题 action 区、右侧栏布局同步和 chat 切换链路
    + 系统指令展开态必须与知识库展开态显式分流，避免共用同一个状态位导致语义串线
    + “系统指令是否展开”只能保存在页面运行时状态，不得写入 chat 持久化字段、`saveChats()`、`localStorage` 或 URL
    + chat 切换、右侧边栏收起、知识库进入展开态等场景下，都必须显式回收系统指令展开态，避免残留脏状态
    + 日志流式追加期间，展开态切换不得中断现有 CLI 子面板渲染、恢复和滚动沉底逻辑
    + 新按钮的 DOM 落位、显隐和 aria 文案必须稳定，禁止在不同状态下漂移到标题栏之外
    + 能用现有开源包和浏览器能力的就不要重复造轮子
+ 最小范围更新
