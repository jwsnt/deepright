# 20260709-1 用户手册

本次迭代为历史很多的旧会话补充了“冷历史”轻量恢复。首次进入当前页面里还没有展示过中心消息的历史会话时，页面不再一次性恢复整段历史，而是先恢复最近 `N` 条原始记录，再补齐到“最老完整请求轮次”的起点。

## 触发条件

- 只有当前 `chat` 在当前页面还没有任何已展示中心消息时，首次切入才会进入冷历史模式
- 只要该 `chat` 已经在前端展示过内容，后续再次切回时会继续复用现有展示窗口和恢复状态，不会重新走冷历史首屏
- 正在执行任务中的会话、页面刷新后需要继续恢复的会话，以及其他命中现有 `/api/restore` 或 `SSE` 恢复链路的场景，都会直接让位给原有恢复逻辑

## 首屏恢复规则

- 首屏会先恢复最近 `N` 条原始记录，而不是把整段历史一次性塞进前端内存、DOM 和本地缓存
- 如果这批记录的最老位置仍落在某轮请求中间，页面会继续向前补抓，直到补齐到“最老完整请求轮次”的起点，或者历史已经耗尽
- 一轮完整请求必须从 `Q` 开始，到后续 `A / cli/get / cli/pub / X / abnormal / done` 全部结束为止
- 因此冷历史不会从半截 assistant 响应、半截 `cli/*` 记录或半截异常片段直接开始渲染；若最早命中的 `Q` 之前还有更老的半截记录，本次也不会展示
- 首屏恢复完成后，页面会提示 `已恢复最近 N 条，更早内容向上滚动继续加载`

## 展示效果

- 冷历史模式下只展示中心区最终态内容，保留用户消息和 assistant 最终正文
- `__PROCESS__`、`__RETRY__`、`__TARGET__` 等过程型特效不会回放，爆炸态也不会重新出现
- 右侧 `CLI` 子任务历史不会在冷历史里恢复，也不会触发对应的子面板闪动
- 这样可以避免历史很多时首次进入会话卡住页面，同时保证正文仍然完整可读

## 向上继续加载

- 用户向上滚动加载更早历史时，会继续沿用“最近一批原始记录 + 向前补齐完整轮次”的策略
- 向上补出来的更早历史，仍然只展示中心区最终态内容，不会重新启用过程特效或右侧 `CLI` 子任务恢复
- 连续多次向上恢复时，历史顺序会保持稳定，不会打乱当前已展示消息
- 插入更早历史后，页面会尽量保持当前阅读位置稳定，避免视图大幅跳动

## 游标与兼容性

- 冷历史模式会额外维护独立的 `chat` 级“向上恢复游标”，专门记录更早历史继续从哪里向前取
- 这个向上游标不会覆盖现有 `lastRestoreAt / lastRestoreId` 或其他等价的向后恢复游标
- 因此现有实时消息流、`/api/restore` 轮询、刷新后 pending 请求恢复、过程态重建和右侧 `CLI` 子任务恢复语义都保持不变
