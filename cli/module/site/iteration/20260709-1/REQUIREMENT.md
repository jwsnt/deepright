### 需求介绍
+ 居中会话区的历史恢复需要区分“冷历史会话首屏恢复”和“现有实时/刷新恢复”两条链路：
    + 冷历史会话：当前页面上还没有该会话的任何已展示中心消息时，首次进入该会话不再一次性恢复全部历史
    + 现有实时/刷新恢复：保持现有 `/api/restore` 轮询、SSE恢复、正在执行任务时页面刷新后继续恢复的既有语义与展示效果，禁止被本次改造改坏
    + 检查点：
        + 已经在页面展示过内容的会话，后续再切回时不得误走冷历史模式
        + 正在执行任务中的会话、以及页面刷新后需要继续恢复中的会话，必须继续走现有恢复链路
+ 冷历史会话首次进入时，历史加载改为“最近 N 条原始记录 + 最老完整请求轮次补齐”：
    + 首次进入冷历史会话时，只恢复最近 N 条原始记录，不再默认把整段历史一次性塞进前端内存、DOM 和本地缓存
    + 如果最近 N 条原始记录里的最老位置仍然落在某轮请求中间，必须继续再向前补抓 N 条，直到找到“最老完整请求轮次”的起点，或者历史已经耗尽
    + 首屏恢复完成后，页面需要提示：`已恢复最近 N 条，更早内容向上滚动继续加载`
    + 检查点：
        + 历史很多时，首次进入会话不会一次性卡死页面
        + 若最近 N 条中没有完整轮次起点，必须继续向前补抓，而不是从半截 assistant 响应开始渲染
+ 冷历史会话的渲染边界必须按“完整请求轮次”裁切，而不是按单条 SSE 记录裁切：
    + 一轮请求必须从一条 `Q` 开始，到它后面的 `A / cli/get / cli/pub / X / abnormal / done` 全部结束为止
    + 冷历史模式下禁止从某条中间 `A` 直接开始恢复和渲染
    + 冷历史模式下，如果最早命中的 `Q` 之前还有更老的半截 `A / cli/* / X` 记录，这些半截记录本次不得渲染
    + 检查点：
        + `__PROCESS__`、爆炸态、CLI 子任务相关的 SSE 片段不会因为从半截 `A` 开始而出现错乱
        + 同一轮 user/assistant 对话不会因为首屏裁切而丢掉开头 `Q`
+ 冷历史会话中的历史轮次一律只展示最终态中心内容，不展示 SSE 过程特效：
    + 冷历史模式下恢复出来的历史轮次，只需要展示用户消息与 assistant 最终态正文
    + 冷历史模式下不展示 `__PROCESS__`、`__RETRY__`、`__TARGET__` 等过程型特效
    + 冷历史模式下不恢复、不展示右侧 CLI 子任务历史，也不触发 CLI 子面板闪动
    + 冷历史模式下不要求保留原始 SSE 过程态以支撑上述特效；目标是轻量恢复历史最终展示
    + 检查点：
        + 冷历史首屏不会出现过程态指示、爆炸效果、右侧 CLI 子任务补齐
        + 历史轮次最终正文仍然正确可读，不因移除过程态而丢正文
+ 冷历史会话向上继续恢复更早历史时，继续沿用“完整轮次 + 最终态展示”规则：
    + 用户向上滚动继续恢复更早历史时，仍然按完整请求轮次补齐，不得从半轮中间插入
    + 向上继续恢复出来的更早历史，仍然只展示最终态中心内容，不得在更早历史里重新启用 `__PROCESS__`、`__RETRY__`、`__TARGET__`、CLI 子任务等过程特效
    + 向上恢复每次仍按最近一批原始记录向前取数；若该批最老位置没有完整轮次起点，仍需继续补抓直到补齐或历史耗尽
    + 检查点：
        + 连续多次向上恢复时，页面不会突然出现过程态特效
        + 向上恢复追加的历史顺序稳定，不会打乱现有已展示消息
+ 本次改造必须保留并隔离现有实时 SSE 流响应链路：
    + 用户主动发送消息后的实时 SSE 流式响应、过程态展示、爆炸效果、`CLI@sub`、任务状态提示等现有能力必须保持不变
    + 正在执行任务时页面刷新后触发的现有 `/restore` 恢复能力必须保持不变，包括 pending 请求恢复、过程态重建、右侧 CLI 子任务恢复、终态判断等既有语义
    + 冷历史模式不得复用会修改现有 forward restore 状态的 reducer / 游标 / 展示分支，以免把活跃任务错误地当作静态历史处理
    + 检查点：
        + 实时发送消息后，现有流式 assistant 展示与中途刷新恢复行为完全不回退
        + 只有冷历史首屏和后续向上恢复命中新的简化历史逻辑
+ 冷历史模式需要引入独立的 chat 级别“向上恢复游标”，但不得破坏现有向后恢复游标系统：
    + 现有用于 `/restore` 向后增量恢复、轮询、刷新恢复的 chat 级别游标语义保持不变，不允许被冷历史逻辑覆写
    + 新增的向上恢复游标也必须是 chat 级别，用于记录“更早历史继续从哪里向前取”，与现有向后恢复游标彻底分离
    + 冷历史首屏恢复和向上恢复只能读写自己的向上游标，不得覆盖现有 `lastRestoreAt / lastRestoreId` 或等价 forward restore 状态
    + 检查点：
        + 冷历史向上恢复后，再次触发实时 `/restore` 时不会丢失或错乱现有恢复位置
        + 同一 chat 的向上恢复位置可持续推进，但不会影响后续新消息恢复
+ 冷历史模式的触发与退出需要可判定、可回退：
    + 只有当当前 chat 还没有任何已展示中心消息时，才允许首次进入冷历史模式
    + 一旦该 chat 已经有了前端展示内容，后续该 chat 再次切换展示时应复用现有已展示窗口与已有恢复状态，而不是再次从冷历史首屏逻辑重建
    + 冷历史模式若发现当前 chat 实际处于现有实时恢复链路中，必须立即让位给现有恢复链路
    + 检查点：
        + 同一个 chat 不会在冷历史模式和现有恢复模式之间来回抖动
        + 冷历史模式只作为“首次无展示内容进入该 chat”的轻量首屏策略存在
