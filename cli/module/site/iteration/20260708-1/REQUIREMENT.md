### 需求介绍
+ 当前站点把会话历史整包写入浏览器 `localStorage`
    + 聊天主存储 key 仍为 `CHATS_KEY = 'deepright_chats'`
    + 当前保存内容除了消息正文，还会携带 `cliCommandHistory`、`thinking/verify/htmlOutput/swarm` 等会话级状态
    + assistant 消息在部分场景下还会落盘 `rawSse`，这会与最终 `content` 形成重复存储
+ 当本地 `localStorage` 配额接近上限时，不能再只依赖浏览器抛错后直接提示失败
    + 现状是用户会看到“本地存储已满，新的会话历史暂未保存”
    + 这会导致本次对话中的新增历史不能稳定落盘
    + 需要在保持现有前端技术栈不变的前提下，补一套最小侵入的本地存储压缩策略
+ `saveChats()` 需要支持分级压缩保存，并遵循“先删冗余、再删次要历史、最后才丢更多正文”的顺序
    + 第一优先级：在配额不足时，优先移除已完成 assistant 消息中仅用于恢复/回放的 `rawSse`
    + 第二优先级：继续压缩非活跃会话与活跃会话的 `cliCommandHistory`
    + 第三优先级：继续压缩非活跃会话的消息窗口，再在必要时压缩活跃会话的已完成消息窗口
    + 每一轮压缩都必须基于待写入 payload 操作，避免破坏当前运行时内存态
+ 新策略必须保留当前仍在进行中的会话恢复能力
    + 对 `pendingRequest = true` 的会话，不能在第一轮压缩里直接移除其 `rawSse`
    + 避免破坏依赖 `rawSse` 的恢复逻辑、任务 badge 恢复、底部 inline hint 恢复等现有行为
    + 只有在更激进的降级阶段，才允许对所有会话统一丢弃 `rawSse`
+ 存储告警语义需要与压缩结果保持一致
    + 如果只是成功压缩后写入，应提示“本地存储空间不足，已仅保存最近部分会话历史”
    + 如果经过多轮压缩仍然无法写入，才提示“本地存储已满，新的会话历史暂未保存”
    + 不允许在真实保存失败时继续表现为成功
+ 本次需求不引入新的持久化介质迁移
    + 不要求把聊天正文迁移到 `IndexedDB`
    + 不新增新的设置面板、用户开关或清理入口
    + 仅在现有 `index.html` 的存储链路内完成最小范围修复
+ 本次需求需要同步编写用户手册
    + 手册中需要说明当前本地存储爆满的原因：聊天历史与部分流式原始记录共同占用 `localStorage`
    + 手册中需要说明新的分级压缩顺序：先删 `rawSse`，再裁剪 CLI 历史，再裁剪消息窗口
    + 手册中需要说明两类提示文案分别对应“压缩后已保存部分历史”和“压缩后仍无法保存”
