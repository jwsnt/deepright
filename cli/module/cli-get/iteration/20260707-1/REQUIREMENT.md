### 需求介绍
+ 现有 `cli/get -> worker pool -> exec -> cli/pub` 链路中，如果 worker pool 没有空闲 worker，`cli/get` 主心跳会在提交任务时被阻塞，导致无法继续快速拉取后续任务
+ 本次迭代目标：
    + `cli/get` 主心跳不允许因为 worker 数不足而阻塞
    + 允许任务在客户端本地排队，以提升任务下发吞吐
    + 不要求严格不丢任务，不需要做服务端 ACK / 客户端持久化补偿
    + 保持现有 `cli/get` / `cli/pub` 协议不变，不新增上游接口

+ 新增本地内存有界任务队列：
    + 新增命令行参数 `--queue`
        + 含义：本地待执行任务队列最大容量
        + 默认值：`1000`
    + 队列仅保存在本地内存中，不写入 sqlite，不做持久化恢复
    + 进程退出、崩溃、重启后，队列中尚未执行或尚未回传的任务允许丢失

+ `cli/get` 主循环调整为“先判队列，再拉任务”：
    + 主循环每次准备请求 `/cli/get` 前，必须先检查本地任务队列是否还有空位
    + 只有本地任务队列有空位时，才允许发起 `/cli/get`
    + 如果本地任务队列已满：
        + 不允许发起 `/cli/get`
        + 不允许继续从服务端取任务后再发现本地放不下
        + 直接等待由 `--sleep` 指定的毫秒数后再次检查队列剩余容量
    + 当 `/cli/get` 成功返回任务时：
        + 必须先将任务放入本地内存队列
        + 只要成功入队，即视为本轮任务接收完成
        + 入队完成后主循环立即继续下一次容量检查和 `/cli/get` 拉取，不等待 worker
    + 这样主循环与 worker 执行彻底解耦：
        + 主循环只负责“判断队列容量 -> 拉任务 -> 入队”
        + worker 只负责“出队 -> 执行 -> 交给发布链路”

+ worker pool 与本地任务队列的职责拆分：
    + `--thread` 仍表示执行 worker pool 大小，默认值保持当前最新默认值 `20`
    + 本地队列是 worker 的上游缓冲区，不替代 worker pool
    + worker 不再由 `/cli/get` 线程直接 `Submit(task)` 获取任务，而是从本地队列持续消费
    + 允许队列中任务数大于 worker 数，前提是未超过 `--queue`

+ `ddl` 过期校验改为“出队执行前校验”：
    + `cli/get` 响应任务中已有 `ddl` 属性，定义见 `../../REQUIREMENT.md`
    + 任务进入本地队列后，真正被 worker 取出准备执行时，必须重新检查当前时间戳是否超过 `ddl`
    + 如果当前时间已经大于 `ddl`：
        + 不允许执行该任务
        + 打印明确日志，至少包含 `agentId`、`chat`、`tid`、`ddl`、当前时间、`cmd`
        + 直接丢弃该任务
        + 不需要进入 `cli/pub`
    + 如果 `ddl` 未超时，则按现有逻辑继续执行
    + 由于排队期间可能等待较久，不允许只在 `/cli/get` 响应解析时校验一次

+ 排队任务不支持取消：
    + 本次迭代明确不支持取消本地队列中尚未开始执行的任务
    + `/api/kill` 或同等 kill 能力仅保持对“已开始执行、已注册到活跃命令表”的任务生效
    + 处于本地内存队列中、尚未开始执行的任务，不需要额外提供删除、跳过、撤销接口

+ 新增“执行”和“发布”两段式流水线：
    + 为避免 `cli/pub` 重试等待占住执行 worker，本次迭代必须拆成两段：
        + `taskQueue -> execute worker -> publishQueue -> publish worker`
    + 执行 worker 的职责：
        + 从本地任务队列取任务
        + 校验 `ddl`
        + 执行命令或沙盒命令
        + 生成待回传结果
        + 将待回传结果放入本地发布队列
    + 发布 worker 的职责：
        + 从本地发布队列取结果
        + 调用 `/cli/pub`
        + 根据重试策略决定是否延迟重试
    + 执行 worker 不允许因为 `cli/pub` 的等待重试而长时间阻塞

+ 新增本地内存发布队列与发布重试策略：
    + 发布链路新增命令行参数：
        + `--retry_interval`
            + 含义：`cli/pub` 失败后的下一次重试等待时间（毫秒）
            + 默认值：`10000`
        + `--retry_times`
            + 含义：单条结果在首次发布失败后允许再次尝试的次数
            + 默认值：`1`
            + 说明：默认值 `1` 表示“首次发布失败后，额外重试一次”
    + “发布失败”定义包括但不限于：
        + 发起 `/cli/pub` 请求时出现网络错误
        + 请求超时
        + HTTP Status Code 非 `200`
        + 响应报文解析失败
        + 响应 JSON 中 `code != 200`
    + 发布 worker 处理规则：
        + 首次发布成功：任务完成，直接结束
        + 首次发布失败且剩余可重试次数 > 0：
            + 等待 `--retry_interval` 指定毫秒数
            + 再次发起 `/cli/pub`
        + 当失败次数超过 `--retry_times` 后：
            + 打印明确失败日志，至少包含 `agentId`、`chat`、`tid`、失败次数、最后一次错误
            + 允许直接丢弃该结果
            + 不要求持久化补偿

+ `cli/pub` 重试允许重复回传：
    + 本次迭代接受以下现实语义：
        + 如果服务端已经收到结果，但客户端因为超时或其他异常未收到成功响应，则客户端可能按重试策略再次推送同一个 `tid`
    + 由于服务端整体是 pub/sub 模式，本次迭代不要求客户端新增去重机制
    + 不需要因为可能重复推送而阻止重试策略落地

+ 与现有功能的兼容要求：
    + 不允许修改 `cli/get` 和 `cli/pub` 报文 schema
    + 不允许破坏现有：
        + 沙盒模式判断
        + `subOps.exempted` 豁免逻辑
        + 活跃命令注册 / 注销
        + `/api/kill` 对运行中命令的终止能力
        + `message_insert` 随 `cli/pub` 一起上报的现有逻辑
    + 如果任务因 `ddl` 过期被本地丢弃，则不进入现有 `cli/pub + message_insert` 上报逻辑

+ integration 同步要求：
    + `integration` 内置的 `cli-get` 链路必须同步相同能力与默认值：
        + `--queue=1000`
        + `--retry_interval=10000`
        + `--retry_times=1`
        + 执行队列 / 发布队列两段式流水线
        + `ddl` 出队执行前校验
    + 不允许只修改独立 `cli-get` 而遗漏 `integration` 收口实现
    + `integration` 的手册、默认配置、日志行为与独立 `cli-get` 保持一致语义

+ 日志要求：
    + 至少新增以下日志场景：
        + 本地任务队列满，跳过 `/cli/get`
        + 任务成功入本地队列
        + worker 出队前发现 `ddl` 超时并丢弃
        + 执行结果进入发布队列
        + `/cli/pub` 首次失败、开始等待重试
        + `/cli/pub` 重试成功
        + `/cli/pub` 超过最大重试次数后放弃
    + 日志内容应可定位具体任务，至少包含 `tid`
