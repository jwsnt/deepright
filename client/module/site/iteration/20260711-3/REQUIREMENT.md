### 需求介绍
+ 本次还需要补足 site 前端本地存储预算治理，避免 `localStorage` 长时间膨胀后再次出现“本地存储已满，新的会话历史暂未保存”：
    + 当前主要问题不是 `theme`、侧边栏折叠、引导标记等轻量 key，而是 `deepright_chats` 中的聊天正文、`rawSse` 与 `cliCommandHistory` 累积后持续变大
    + 其中 `cliCommandHistory` 的 `output` 文本可能远大于 `command` 本身，若允许长期累积，很容易把单个 chat 顶到数 MB
    + 本次目标不是完全取消本地历史，而是给 `site` 前端增加一套“可持续运行的本地存储预算控制”，避免问题只靠用户手工清理
+ 本次本地存储治理的核心目标如下：
    + 以当前页面 origin 下的 `localStorage` 总占用作为预算判断依据，而不是只看单个 key
    + 当本地存储总占用超过 `2.5 MB` 时，页面需要自动触发压缩治理，而不是等到浏览器真正抛出 quota error 后才被动兜底
    + 自动压缩后的目标体积收口为约 `1.5 MB`，要求留出稳定余量，避免刚压缩完又立刻反复打满
    + 自动压缩应优先保留“最近、可见、当前仍有用”的历史，牺牲“重复、冗余、低价值”的本地副本
+ `cliCommandHistory` 的长期持久化策略需要显式收紧：
    + 每个 chat 持久化到 `localStorage` 的 `cliCommandHistory` 只保留最近 `30` 条
    + 右侧 CLI 子面板用于展示/恢复的 CLI 历史同样只保留最近 `30` 条，禁止出现“面板只展示少量、但本地仍无限堆积”的不一致状态
    + 这里的 `30` 条限制适用于手动命令记录、restore 恢复出的命令记录、live 恢复出的命令记录，要求统一收口
    + 本次需求不要求保留完整 CLI 长历史；超过窗口上限的更早命令允许被自动淘汰
+ 本地存储压缩必须是“主动维护 + 被动兜底”双机制：
    + 主动维护：
        + 页面初始化完成后，需要启动定时巡检
        + 巡检周期收口为 `30s` 一次
        + 当页面从后台重新切回前台可见时，也要补做一次预算检查
        + 正常 `saveChats()` 成功后，也应顺手做一次预算检查，避免体积只增不减
    + 被动兜底：
        + 若实际写入 `localStorage` 时仍遇到 quota error，现有 fallback 压缩能力仍需保留
        + 主动维护不能替代 quota error 兜底，只能尽量减少真正写爆的概率
+ 自动压缩的优先级必须可解释、可维护：
    + 第一优先级：继续保留当前 chat 与近期聊天正文，优先压缩明显冗余的副本字段
    + 第二优先级：优先删除已完成 assistant 消息里仅用于恢复/重放的 `rawSse`，因为这类字段往往是高体积、低长期价值的重复信息
    + 第三优先级：优先裁剪非活跃 chat 的 CLI 历史与消息条数，再视预算压力决定是否继续裁剪当前 chat 的本地副本
    + 第四优先级：CLI 历史的裁剪应优先于破坏正文可读性的消息裁剪
    + 自动压缩的核心目标是“尽可能保住可直接阅读的中心会话正文”，而不是机械平均裁剪所有字段
+ 自动压缩的运行边界必须安全：
    + 当存在全局进行中的 SSE / 恢复流式响应时，不应在中途做本地压缩，以免扰动当前消息恢复与流式状态
    + 自动压缩后必须把压缩后的 payload 同步回运行时内存与当前 UI，避免出现“localStorage 已变小，但页面仍持有旧大对象”的状态分裂
    + 若当前 active chat 因裁剪被影响，聊天主区、CLI 子面板、右侧 URL 预览等依赖 chat 数据的 UI 都需要同步刷新
+ 自动压缩的用户感知需要克制：
    + 自动维护属于后台治理能力，不应频繁弹 toast 打扰用户
    + 只有在确实发生了超过预算后的自动压缩时，才允许给出一次轻量提醒
    + 正常保存成功后的预算巡检若未发生压缩，不需要额外提示
+ 本次需求的验收重点如下：
    + 连续使用页面、执行大量 CLI 命令、恢复较多历史后，`localStorage` 体积不会无限增长
    + 当总占用超过 `2.5 MB` 时，页面会自动把历史压回约 `1.5 MB`
    + `deepright_settings`、`theme`、引导标记等轻量 key 不应成为主要压缩目标
    + `cliCommandHistory` 不再成为单个会话占用数 MB 的长期来源
    + 主动维护失败时，原有 quota error fallback 仍然可用，不得因为新机制反而让“已满后无法保存”更早暴露

### 最新实现收口
+ 当前最新实现已经从“仅在 `../../index.html` 内补一个首屏 loading”扩展为“两段式轻量接管”，用于同时覆盖“浏览器刚打开时的白屏”和“`index.html` 已执行后的初始化接管”：
    + 第一段为 integration 层的轻量级 `/launch` 过渡页：
        + 浏览器首次打开时，先进入 `/launch`，而不是直接打开较重的 `/site/?v=...#app`
        + `/launch` 必须保持极轻，只负责显示极简启动文案与按钮，并在浏览器内轮询 `/site/` 是否可用
        + 当前正式文案收口为两行居中状态：
            + 第一行：`正在启动`
            + 第二行默认：`等待完成`
            + 第二行在重试次数较多时升级为：`首次打开新安装包时，页面资源可能还在准备`
            + 按钮文案保持：`立即重试`
        + `/launch` 检测到 `/site/` 已可访问后，应立即 `location.replace(...)` 跳转到真正的 `../../index.html` 对应地址，不得在该页停留过久
        + `/launch` 的职责是兜底“浏览器冷启动 + 新包冷缓存 + 首次导航尚未真正进入主页面”的空白阶段，不承接主页面初始化本身
    + 第二段为 `../../index.html` 内的 boot loading overlay：
        + 当浏览器已经进入 `../../index.html` 并开始执行脚本后，应尽快展示主页面内的轻量 boot loading 提醒，而不是继续空白
        + boot loading overlay 的职责仍然是“等待主页面基础骨架接管”，不是等待所有异步初始化全部结束
        + 一旦主页面基础可见且完成接管，overlay 必须立即释放，不得继续挡住后续的 token、插件状态、知识库、历史恢复等异步补齐流程
+ 因此本次需求的最新验收口径更新为：
    + 若首包首次打开时，浏览器还未真正进入 `../../index.html`，应先看到 `/launch` 的轻量启动页，而不是无反馈空白
    + 若已经进入 `../../index.html`，则应尽快看到页面内 boot loading 提醒，并在主页面基础可见后立即让位
    + `/launch` 与 `../../index.html` 内 boot loading 属于不同层级的 loading 语义，禁止混用状态位，但视觉上应保持同一套“正式、克制、轻量”的启动感
+ 本文档前文中“只解决 `index.html` 开始执行后的前端白屏感知”这一边界，保留为原始前端原则；但当前最新实现允许在 integration 启动入口增加一个极轻量的浏览器过渡页，以便补足 `index.html` 真正接管前的空白感知问题
+ 与此同时，本次本地存储治理的最新实现收口更新为：
    + `site` 侧需要把 `localStorage` 预算控制做成常驻运行时能力，而不是一次性脚本
    + 当前正式收口阈值如下：
        + 超限触发阈值：`2.5 MB`
        + 自动压缩目标：约 `1.5 MB`
        + 定时巡检周期：`30s`
        + 每个 chat 保留的 `cliCommandHistory` 上限：最近 `30` 条
        + 右侧 CLI 子面板可展示/恢复的 CLI 历史上限：最近 `30` 条
    + 当前正式收口的自动治理触发点如下：
        + 页面初始化完成后启动定时巡检
        + 页面从隐藏切回可见时执行一次预算检查
        + `saveChats()` 正常写入后立即执行一次静默预算检查
        + 若写入阶段直接触发 quota error，则继续走现有 fallback 压缩链路
    + 当前正式收口的压缩顺序如下：
        + 先统一规整 chat payload，使 `cliCommandHistory` 只保留最近 `30` 条
        + 再优先删除已完成 assistant 消息中的 `rawSse`
        + 再优先压缩非活跃 chat 的 CLI 历史和消息条数
        + 若仍未满足预算目标，才允许继续压缩活跃 chat 的冗余本地历史
    + 当前正式收口的运行边界如下：
        + 当存在全局进行中的 SSE / restore 流式响应时，自动治理暂不执行
        + 一旦自动治理生效，压缩后的 chat payload 必须同步回运行时状态并刷新当前 chat 相关 UI
        + 自动治理默认静默运行，只在首次真实发生“超过 `2.5 MB` 后自动压缩”时提示一次轻量 toast
    + 因此本次本地存储治理的验收口径更新为：
        + 前端在高频使用、反复恢复、频繁执行 CLI 命令的情况下，不能再把本地存储无限推高
        + 自动治理应把问题前移到“超过预算即维护”，而不是等浏览器正式拒绝写入后才暴露
        + `cliCommandHistory` 的历史窗口必须被严格限制，禁止再次出现单个 chat 仅 CLI 历史就占用数 MB 的实现
        + 自动治理不得破坏当前进行中的流式响应，也不得引入明显闪烁、重复重建或界面错乱

### 编写代码

    + 首屏预加载提醒与现有局部 loading 语义必须显式分流，避免与右侧 iframe loading、知识库 loading、上传锁定、插件锁定等状态共用同一标记位
    + 本次新增的本地存储预算治理，也必须与现有首屏 loading、局部 loading、历史恢复锁等语义显式分流，禁止复用错误状态位
    + 预加载提醒的出现与消失都必须保持页面稳定，不允许因为切换提醒导致整体布局明显跳动、滚动错位或首屏 reflow 过重
    + 不得通过新增串行 `await` 或人为延迟正常页面渲染来“配合” loading 展示时长
    + 如果需要超时或失败兜底，必须优先复用现有 toast / 提示能力或最小范围新增文案，不做重型异常页
    + 能用现有开源包和浏览器能力的就不要重复造轮子
    + 本地存储预算计算必须按当前 origin 下 `localStorage` 总占用估算，而不是只看 `deepright_chats` 单个 key
    + 自动压缩逻辑必须尽量复用现有 chat payload 构建、压缩、fallback 代码路径，不允许新造一套独立且难以维护的本地存储序列化体系
