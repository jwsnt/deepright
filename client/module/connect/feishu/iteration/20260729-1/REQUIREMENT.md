### 需求介绍
+ 飞书插件保持既有 `param` 元数据契约：字段 key 固定为 `appId`、`appSecret`、`mcp_url`，`name` 命令继续返回展示信息但不得替代 `key=feishu` 作为配置、生命周期或运行时查找标识。不得改变现有 CLI 子命令、参数名称、报文 Schema、Connect/Integration 收口方式或其他既定插件规则。
+ 对 `start` 及已启动实例的重启，服务端必须在读取 `key=feishu` 的已保存 meta 后执行以下配置校验；命令行、页面和其他调用方均必须得到一致结果：
  + `appId`、`appSecret` 均为非空（忽略首尾空白）时，凭证组有效，`mcp_url` 可空可非空。
  + `appId`、`appSecret` 只有一个非空时，启动／重启失败，明确返回缺失的凭证组错误。
  + 两个凭证均为空且 `mcp_url` 非空时，配置有效，启动／重启必须成功。
  + 三个字段均为空时，启动／重启失败，明确返回“至少填写 appId 与 appSecret，或 mcp_url”的等价错误。
+ 当凭证组有效时，保持既有飞书长连接行为：执行现有凭证校验、创建会话并运行长连接；该行为不因 `mcp_url` 是否填写而改变。
+ 当仅 `mcp_url` 有效时，插件必须按既有生命周期返回并保持“已启动”状态，允许后续按既有关闭流程关闭；不得调用飞书凭证校验、创建飞书会话、建立飞书长连接、进入长连接重试循环或进行飞书收发。该模式仅表示 MCP 地址配置已被插件成功接收和运行态已启动，不代表已连接飞书。
+ 启动、重启和运行态分支都必须记录日志：至少可区分“凭证组启动并尝试／建立长连接”“仅 mcp_url 启动、未建立长连接”“配置校验失败”。日志不得输出 `appSecret` 的明文，也不得将完整敏感配置对象写入日志；可记录是否填写凭证组、是否填写 `mcp_url`、插件 key、启动／重启结果和失败原因。
+ 本次规则取代此前“`mcp_url` 缺省且不影响空凭证启动”的启动语义：`mcp_url` 本身仍是可选字段，但三项配置整体必须至少提供完整凭证组或非空 `mcp_url` 之一。
+ 既有仅用于测试的 `mode=mock` 分支保持原有行为，不从页面参数暴露，也不作为生产配置绕过上述规则的方式。

### 编写代码
+ 以Golang编写以上代码，要求：
    + 编译应用名：feishu
    + 能用开源包的就用开源包
    + 代码简洁，包体积越小越好
+ 作为其他模块可以调用的子模块和可独立运行的CLI命令来编写
+ 启动前校验必须放在服务端共用生命周期路径，不能只依赖页面校验；前台 `start`、后台 `start`、重启和直接 CLI 调用必须复用同一规则。
+ 仅 `mcp_url` 模式须使用明确的无长连接运行分支并维持既有 PID／状态语义，避免进程立即退出后被误报为未启动；关闭、状态查询和日志读取继续复用现有生命周期实现。
+ 继续使用 meta 的 `key=feishu` 查询配置，不得改用 `name`；继续使用 JSON 字段 `appId`、`appSecret`、`mcp_url`，不为此需求引入新的配置字段或迁移。
+ 覆盖自动化测试：完整凭证组启动并创建长连接；完整凭证组加 `mcp_url` 仍创建长连接；仅 `mcp_url` 启动成功且不触发凭证校验／会话创建；仅一个凭证和三项为空启动失败；重启沿用相同分支；日志包含结果但不泄露 `appSecret`。
