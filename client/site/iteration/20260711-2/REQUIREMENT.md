### 需求介绍
+ Site 首次打开时，需要把“长时间空白页”改为“轻量级预加载提醒 + 正常页面渐进接管”：
    + 当前问题是用户首次进入 `/site/` 时，在页面真正可交互前会看到明显空白区域，缺少及时反馈
    + 本次目标不是在视觉上继续放大启动动画，而是提供一个成本很低、立即可见、不会额外拖慢首屏的加载提醒
    + 页面完成基础可见渲染后，应尽快切换到现有正常页面，而不是让用户持续停留在单独的 loading 页
+ 预加载提醒必须追求“快速反馈”，而不是等待全部初始化完成：
    + 用户一进入页面，只要浏览器已经拿到并开始解析 `index.html`，就应该尽快看到居中的 `正在加载中` 或等价轻量文案
    + 该提醒的职责是消除“空白无反馈”，不是阻塞用户直到所有异步初始化都结束
    + 预加载提醒消失的时机必须定义为“首屏基础骨架已可见且主页面已接管”，禁止定义成“所有初始化请求都完成”
    + 检查点：
        + 首次进入页面时，用户先看到的是轻量提醒，而不是大片空白页
        + 首屏主体一旦具备基础可见性，提醒应立即让位，不得继续遮挡页面等待 token、插件状态、知识库、历史恢复等后续请求
+ 预加载提醒本身必须是轻量级实现，不能为了提示而再次增加首屏负担：
    + 提醒应优先使用原生 HTML / CSS 实现，可包含极简文案、轻微透明层、简单脉冲或点状动画，但不得依赖额外图片、额外字体、复杂 canvas 或重型动画
    + 不允许为了这个提醒新增新的构建流程、前端依赖或额外网络请求
    + 提醒样式需要兼容现有浅色/深色主题，避免出现强烈割裂或过重视觉噪音
    + 检查点：
        + 提醒自身代码足够轻，不会让页面因为先渲染 loading 而更慢
        + 在低功耗或节能场景下，提醒仍然能正常展示，必要时可自动降级为纯文案
+ 本次需求只解决“前端首屏感知白屏”，不把责任错误扩大到 HTML 返回前的阶段：
    + 若浏览器在拿到 `index.html` 之前已经卡住，例如静态文件响应慢、网络阻塞、服务端未返回，本次前端预加载提醒无法提前展示
    + 因此前端验收边界应明确为：从 `index.html` 开始执行后，页面不得继续长时间保持空白无反馈
    + 本次改造不要求同时解决服务端静态资源返回速度问题，但实现上不得掩盖真实慢点
+ 预加载提醒与现有初始化链路必须显式分层：
    + 现有 `init()` 中的设置加载、token 补全、插件元数据、插件状态、聊天记录恢复、右侧面板初始化等逻辑继续按原职责工作
    + 新增提醒只负责“页面还未完成首屏接管时的即时反馈”，不得把原有异步初始化全部强绑到一个必须等待的总锁上
    + 不允许为了控制提醒显隐，把原本可并行或可延后的初始化重新串成更重的阻塞链路
    + 检查点：
        + 新增提醒后，首屏不应因为人为等待更多初始化而变慢
        + 正常页面出现后，后续异步数据仍可按原方式陆续补齐
+ 预加载提醒的结束条件必须可判定、可维护、可回退：
    + 需要有明确运行时状态表示“当前仍处于首屏预加载阶段”与“主页面已接管”
    + 一旦主页面接管完成，提醒应平滑隐藏或直接移除，不得反复闪现、重复挂载或在会话切换时重新冒出
    + 页面后续的普通刷新数据、切换 chat、刷新知识库、重载右侧预览等行为，都不应再次触发这次“首次打开预加载提醒”
    + 检查点：
        + 预加载提醒只在真正的首次进入页面阶段生效
        + 初始化后不会残留不可点击遮罩、不可见挡板或错误的 z-index 覆盖
+ 当初始化明显变慢或失败时，需要给出比纯空白更可理解的反馈：
    + 若页面在合理时间内仍未完成首屏接管，可将文案升级为“仍在加载，请稍候”或等价提示，但依然保持轻量
    + 若初始化发生明确错误，页面应避免继续停留在无意义的 loading 状态；可以复用现有错误提示、toast 或降级提示文案
    + 本次不强制要求新增完整重试面板，但至少不能让用户无限面对“看起来还在加载、实际已失败”的假状态
    + 检查点：
        + 超时场景下用户能区分“还在加载”与“页面可能异常”
        + 失败后不会永久停留在 loading 遮罩下
+ 预加载提醒的交互与可访问性需要保持基本可用：
    + 提醒展示期间不要求页面可完整交互，但应避免出现焦点陷阱、键盘无法恢复、屏幕阅读器重复播报等明显问题
    + 文案需要简洁明确，避免使用模糊表达；若包含状态切换文案，也要保持前后一致
    + 若提醒采用遮罩层，其层级应只覆盖首屏等待阶段，结束后必须完全释放点击与滚动命中
+ 本次实现必须继续遵守 site 现有前端收口方式：
    + 在 `../../index.html` 内按现有 HTML / CSS / JavaScript 组织实现，不引入新的构建流程或前端依赖
    + 代码尽量复用现有页面根容器、主题状态、低功耗降级与初始化时序控制能力，避免额外造一套启动页框架
    + 若需要新增运行时状态或样式类名，命名应聚焦“首屏预加载”语义，避免与现有右侧 iframe loading、知识库 loading、上传锁定等状态混淆

### 最新实现收口
+ 当前最新实现已经从“仅在 `../../index.html` 内补一个首屏 loading”扩展为“两段式轻量接管”，用于同时覆盖“浏览器刚打开时的白屏”和“`index.html` 已执行后的初始化接管”：
    + 第一段为 integration 层的轻量级 `/launch` 过渡页：
        + 浏览器首次打开时，先进入 `/launch`，而不是直接打开较重的 `/site/?v=...#app`
        + `/launch` 必须保持极轻，只负责显示极简启动文案与按钮，并在浏览器内轮询 `/site/` 是否可用
        + 当前正式文案收口为两行居中状态：
            + 第一行：`正在启动`
            + 第二行默认：`等待完成`
            + 第二行在重试次数较多时升级为：`首次打开新安装包时，页面资源可能还在准备`
            + 按钮文案保持：`立即重试`
        + `/launch` 检测到 `/site/` 已可访问后，应立即 `location.replace(...)` 跳转到真正的 `../../index.html` 对应地址，不得在该页停留过久
        + `/launch` 的职责是兜底“浏览器冷启动 + 新包冷缓存 + 首次导航尚未真正进入主页面”的空白阶段，不承接主页面初始化本身
    + 第二段为 `../../index.html` 内的 boot loading overlay：
        + 当浏览器已经进入 `../../index.html` 并开始执行脚本后，应尽快展示主页面内的轻量 boot loading 提醒，而不是继续空白
        + boot loading overlay 的职责仍然是“等待主页面基础骨架接管”，不是等待所有异步初始化全部结束
        + 一旦主页面基础可见且完成接管，overlay 必须立即释放，不得继续挡住后续的 token、插件状态、知识库、历史恢复等异步补齐流程
+ 因此本次需求的最新验收口径更新为：
    + 若首包首次打开时，浏览器还未真正进入 `../../index.html`，应先看到 `/launch` 的轻量启动页，而不是无反馈空白
    + 若已经进入 `../../index.html`，则应尽快看到页面内 boot loading 提醒，并在主页面基础可见后立即让位
    + `/launch` 与 `../../index.html` 内 boot loading 属于不同层级的 loading 语义，禁止混用状态位，但视觉上应保持同一套“正式、克制、轻量”的启动感
+ 本文档前文中“只解决 `index.html` 开始执行后的前端白屏感知”这一边界，保留为原始前端原则；但当前最新实现允许在 integration 启动入口增加一个极轻量的浏览器过渡页，以便补足 `index.html` 真正接管前的空白感知问题

### 编写代码
+ 以现有site页面技术栈编写以上代码，要求：
    + 在../../index.html中按现有HTML/CSS/JavaScript组织方式实现
    + 不引入新的构建流程和额外运行时依赖
    + 代码简洁，尽量复用现有根容器、主题切换、低功耗渲染和初始化入口逻辑
    + 首屏预加载提醒与现有局部 loading 语义必须显式分流，避免与右侧 iframe loading、知识库 loading、上传锁定、插件锁定等状态共用同一标记位
    + 预加载提醒的出现与消失都必须保持页面稳定，不允许因为切换提醒导致整体布局明显跳动、滚动错位或首屏 reflow 过重

    + 如果需要超时或失败兜底，必须优先复用现有 toast / 提示能力或最小范围新增文案，不做重型异常页
    + 能用现有开源包和浏览器能力的就不要重复造轮子
