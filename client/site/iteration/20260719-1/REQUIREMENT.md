### 需求介绍
+ 本次收口会话恢复的查询边界、冷历史分页和切换会话时的重复恢复行为；会话的唯一恢复维度固定为 `chatId`，不得为性能目的改变为必须按 `agentId` 隔离。
+ `/api/restore` 的数据范围需要明确区分：
    + 前向恢复继续按 `chatId + timeline + lastId` 获取该会话游标之后的 `Q`、`A`、`X` 记录；正在执行的会话可继续合并实时 `cli/get`、`cli/pub`，用于当前页右侧 CLI 子任务展示。
    + 冷历史使用 `history=1`，只恢复中心会话正文所需的 `Q`、`A`、`X`；不得查询、返回、合并、排序或重建 `cli/get`、`cli/pub` 历史。
    + 已完成会话的右侧 CLI 子任务不做历史恢复；当前页实时运行中的 CLI 仍由 SSE / live poll 维护。若以后需要查看已完成会话的 CLI 历史，必须按用户显式操作设计独立的按需查询，不得重新混入冷历史首屏。
+ `/api/restore` 的兼容性必须保持：路径、HTTP 方法、既有参数、响应 JSON 结构、`status / data / history` 字段、前向恢复的 CLI 合并和前端现有 `Q/A/X` 消息解析逻辑均不得改变；本次只优化 `history=1` 的取数范围和数据库执行方式。
+ 恢复查询的索引和排序必须与 `chatId` 维度一致：
    + `chat_log` 增加以 `chat_id, created_at, id` 为顺序的联合索引，保留现有以 `agent_id` 开头的索引以兼容其他调用方。
    + 前向恢复与冷历史游标均以 `created_at, id` 作为稳定排序和边界；同一时间戳时必须用 `id` 打破平局，避免漏读或重复。
    + 对仍会按 chatId 查询的实时 CLI 事件，同步提供以 `chat_id, created_at, id` 为顺序的查询索引；不得要求前端补传 `agentId` 才能获得稳定性能。
+ 冷历史分页必须在数据库层完成，禁止先读取整个会话、全部 CLI 日志并在内存中合并排序后才截取页面：
    + `limit` 维持“原始日志记录数目标”的兼容语义，默认仍为 120，不改为 120 轮问答。
    + 数据库先按游标之前的 `created_at DESC, id DESC` 获取最近 `limit` 条 `chat_log` 记录；若最早一条落在某轮回答中间，则继续向前补到该轮对应的 `Q`。
    + 返回给页面前按 `created_at ASC, id ASC` 还原顺序；页面首条必须是完整轮次的 `Q`，允许因补齐边界而略多于 `limit` 条。
    + `history.beforeTimeline` 与 `history.beforeId` 必须指向本页最早返回的 `Q`，下一页以该游标继续取更早完整轮次，且不得重复或遗漏记录。
+ 切换会话时必须避免同一会话的无意义重复恢复：
    + 正在接收本地 SSE 实时流的会话，切换回来后直接使用内存中的实时状态；不得安排自动 `/api/restore`，也不得展示“正在恢复会话内容”锁。
    + 已启动恢复轮询的会话，由轮询的首次请求负责恢复；切换逻辑不得在短延时后再次排队自动恢复，也不得因等待该冗余任务继续持有恢复锁。
    + 不处于 SSE 或恢复轮询中的已完成会话，继续使用既有增量恢复或冷历史恢复；不得破坏备忘录查看、异常恢复、历史向上滚动和会话切换的既有语义。
+ 本次验收重点：
    + 同一 chatId 跨 Agent 的历史仍能完整恢复。
    + 冷历史响应不包含 `cli/get` 或 `cli/pub`，且只访问当前页所需的 `chat_log` 记录。
    + 冷历史首屏与继续向上加载都从完整 `Q` 开始，并能使用返回游标无重复地读取更早轮次。
    + SSE 流或恢复轮询已存在时，切换会话不会额外产生第二个自动 `/api/restore` 请求或恢复遮罩。
