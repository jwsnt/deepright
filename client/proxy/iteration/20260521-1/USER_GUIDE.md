# 20260521-1 使用手册

## 目标

本次迭代调整了 `proxy` 中三方待处理消息桥接为一次性任务明细的扫描频率：

- 从“每分钟扫描一次”改为“每30秒扫描一次”
- 命中可桥接的 `add-request` 后，立即落库生成对应 `task_detail`
- 只调整待处理消息桥接频率，不改变普通 cron 明细生成与执行语义

## 背景

`proxy` 会把 `connect add-request` 产生的待处理消息聚合成一次性任务，并写入共享 sqlite 的 `task_meta` / `task_detail`。

本次变更前，这条桥接链路挂在每分钟一次的后台执行循环里，因此从三方消息进入 `add-request` 到生成 `task_detail`，最坏情况需要等待接近 1 分钟。

本次变更后，待处理消息桥接改为独立后台同步流程：

- 服务启动后先立即执行一次扫描
- 之后每30秒再执行一次扫描

## 行为变化

### 扫描频率

- 后台每30秒扫描一次 `add-request` 产生的待处理消息
- 不需要等到普通 cron 执行轮询时才开始桥接

### 生成时机

- 一旦某个插件名下出现满足条件的待处理消息，就会在本轮扫描中立即创建一次性任务
- 生成的 `task_detail.exec_time` 仍然保持“立即执行”语义

### 不变项

- 消息聚合方式不变
- `meta_ref` 保留本轮聚合的全部 request ID
- `META_ID` 仍写入最后一条原始 request 的 ID
- `response_schema` 继承与透传逻辑不变
- 开始通知、完成回推、状态推进逻辑不变
- 普通 cron 元数据展开频率不受本次变更影响

## 典型链路

1. 插件通过 `add-request` 写入待处理消息
2. `proxy` 后台在最多30秒内扫描到该消息
3. 同一插件名下本轮可执行消息被聚合
4. 立即写入一条 `task_meta`
5. 立即写入对应的 `task_detail`
6. 后续仍按原有执行链路向 `/v1/chat/completions` 发起请求并更新状态

## 影响

- `add-request` 到 `task_detail` 的可见延迟缩短到最多约30秒
- 三方消息更快进入任务执行链路
- 该优化只影响桥接等待时间，不改变任务内容和执行结果格式

## 验证方式

可按以下方式验证：

```bash
cd /path/to/deepright/cli/module/proxy
./proxy --agent-dir ./agent
```

写入一条满足桥接条件的待处理消息后，观察：

- 最多约30秒内生成对应 `task_detail`
- 生成后的 `task_type`、`meta_ref`、`chat_id`、`response_schema` 等字段与历史逻辑保持一致
